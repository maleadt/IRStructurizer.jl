# Control-Flow Structurization for a Value-Yielding Nested-Region Target: Is CFGToSCF the Right Model, and Is the Edge Multiplexer the Universal Mechanism?

## TL;DR
- **Keep CFGToSCF/Bahmann as your model.** Of the five algorithm families, only the RVSDG line (Bahmann TACO 2015) and its faithful reimplementation, MLIR's `CFGToSCF.cpp`, both target value-yielding nested regions AND are duplication-free. Relooper, the WASM backend passes, and Ramsey target block/label structured control (not value-carrying regions); StructurizeCFG targets predicated linear flow. CFGToSCF wins outright for your four-op target.
- **Generalize the edge multiplexer to all three roles — it is real, sound, and standard.** MLIR already uses one `EdgeMultiplexer` construction for multi-entry headers (`createSingleEntryBlock`), multi-exit latches (`createSingleExitingLatch`, with the `shouldRepeat` flag carried as an extra arg), and multi-predecessor continuations. Do not special-case. Prefer the multiplexer over controlled node-splitting unconditionally for a duplication-averse target: splitting is worst-case exponential (Carter–Ferrante–Thomborson lower bound 2^(n−1)).
- **Adopt mutate-then-lift.** CFGToSCF physically mutates the CFG (inserts mux/latch/dispatch blocks, redirects edges, invalidates dominance) and only then emits the structured op. This is the more maintainable architecture precisely because the multiplexer normalizes every multi-entry corner case to single-entry *before* the simple lift runs.

## Key Findings

**C1 — CFGToSCF/Bahmann is the correct model.** Classification by (target, duplication-free):

1. **Relooper** (Zakai, *Emscripten: an LLVM-to-JavaScript compiler*, OOPSLA Companion/SPLASH '11, DOI 10.1145/2048147.2048224): target = block/label structured control (JS/WASM `loop`/`if` + labeled `break`/`continue`); **NOT duplication-free** — it duplicates code (and uses a `label` helper variable) to resolve irreducibility, and is a greedy heuristic (so characterized by both Iozzelli and Ramsey ICFP 2022).
2. **Ramsey, *Beyond Relooper*** (ICFP 2022, DOI 10.1145/3547621, *Proc. ACM Program. Lang.* 6(ICFP) Article 90, pp. 1–22): target = structured control for WebAssembly (`if`, `loop`, multilevel `br`); implements the Peterson–Kasami–Tokura 1973 translation. Its contribution is a single-pass functional formulation over the dominator tree (immutable AST, recursion), not duplication-freedom; faithful to PKT it can split nodes for irreducible CFGs. Target is block/label, NOT value-yielding regions.
3. **LLVM WebAssembly backend** (`WebAssemblyFixIrreducibleControlFlow.cpp`, `CFGStackify`): `FixIrreducible` only removes irreducibility and emits a CFG, not structured ops — its own header states the mechanism verbatim: "we fix up multi-entry loops by adding a new block that can dispatch to each of the loop entries, based on the value of a label 'helper' variable… Then the dispatch block is the single entry in the loop," and it is **duplication-free by design**: "We also prioritize code size and do not duplicate code in order to resolve irreducibility." The same file draws the contrast verbatim: "The Relooper emits structured control flow (with ifs etc.), while we emit a CFG." CFGStackify then produces WASM block/loop/br scopes. Target = block/label structured control, NOT value-yielding regions.
4. **LLVM `StructurizeCFG.cpp`** (AMDGPU): target = **predicated linear flow** — it inserts "Flow" blocks and a network of boolean PHI nodes (`BoolTrue`/`BoolFalse`/`BoolPoison`; class fields at `StructurizeCFG.cpp:280-304`), where "the true incoming values express breaks and the false values express continue states" (`StructurizeCFG.cpp:274-277`), linearizing diamonds into two triangles. The WASM file comment notes LLVM's generic structurizer "linearizes control flow, turning diamonds into two triangles, which is both unnecessary and undesirable." Roughly cloning-free, but produces predicated/linearized flow, not nested value regions. This is explicitly the model you are NOT following.
5. **RVSDG line** (Bahmann/Reissmann/Jahre/Meyer, *Perfect Reconstructability of Control Flow from Demand Dependence Graphs*, ACM TACO 11(4) Article 66, 2015, DOI 10.1145/2693261; impls: jlm, numba-rvsdg/numba-scfg): target = **value-yielding nested regions** (γ-nodes = conditionals with symmetric split/join; θ-nodes = tail-controlled loops carrying values). **Duplication-free** — §4.1 Loop Restructuring / §4.2 Branch Restructuring use predication and inserted branches/predicates instead of node cloning; as Reissmann et al. summarize, "CFR avoids the possibility of exponential code blowup by inserting additional predicates and branches instead of cloning nodes."

**Verdict C1:** CFGToSCF (the direct MLIR implementation of Bahmann 2015, per `CFGToSCF.cpp:9-13`) is the only model that is simultaneously (a) value-yielding-region-targeted and (b) duplication-free. It maps θ→your LoopOp and γ→your IfOp natively. No other listed algorithm is a better fit; the WASM/Relooper/Ramsey family targets the wrong IR (labels, not value-regions) and StructurizeCFG targets predicated linear flow. **Keep CFGToSCF.**

**C2 — Edge multiplexer beats controlled node-splitting for your target.**
- *(a) When each is preferred (literature):* Node-splitting (Janssen & Corporaal, *Making Graphs Reducible with Controlled Node Splitting*, ACM TOPLAS 19(6):1031–1052, 1997, DOI 10.1145/267959.269971) is preferred where downstream optimization/scheduling needs genuinely reducible CFGs with no runtime dispatch overhead and code growth is acceptable; CNS minimizes splits/duplicates. Per the paper verbatim: "Straightforward application of node splitting may result in an average code size increase of 235%. CNS with the heuristic limits the increase to only 3%" — and at whole-program scope, "The impact on the total code size of the complete programs is 13.6% for a straightforward application of node splitting." The multiplexer/predication approach (Bahmann §4.1) is preferred where duplication is unacceptable and a small per-iteration dispatch cost is tolerable.
- *(b) Exact costs:* Multiplexer = one discriminator block-argument (added only when >1 distinct successor; `CFGToSCF.cpp:252-254`) + undef/poison fill for inactive entries' args (`CFGToSCF.cpp:309-311`) + an N-way switch via `createCFGSwitchOp` (last case = default; `CFGToSCF.cpp:349-357`) or a compare chain if no native switch + one extra loop-carried value per merged-entry argument set, evaluated every iteration for loop headers. **Confirmed.** Node-splitting = code-size blowup, **worst-case exponential**; the tight lower bound is **Carter, Ferrante & Thomborson, "Folklore Confirmed: Reducible Flow Graphs are Exponentially Larger," POPL 2003 (ACM SIGPLAN Notices 38(1), pp. 106–114, DOI 10.1145/640128.604141)**: verbatim, "We prove that exponential blowup is unavoidable. In particular, we show that any reducible graph that is equivalent to the complete graph on n nodes (or to related bounded-degree control flow graphs) must have at least 2^(n−1) nodes." **Confirmed/corrected** (the bound is 2^(n−1), proven unavoidable).
- *(c) Hybrid:* Yes — a principled hybrid is multiplexer-for-correctness then optionally duplicate only small side-effect-free tails downstream. This is the WASM backend's philosophy ("minimal intervention," dispatch block) plus later peephole tail-duplication, and what CNS formalizes as minimizing duplicate count. CFGToSCF itself does NOT duplicate; it leaves the mux in place. No mainstream value-region compiler couples a hard duplication threshold to the mux today; the cleanest design keeps the mux and treats tail-duplication as a separate, profile/size-gated pass.
- *(d) Verdict:* For a duplication-averse, value-yielding target, **there is essentially no reason to prefer splitting over the multiplexer.** Splitting's only advantage (no per-iteration discriminator) is irrelevant when your invariant forbids duplication and your IR carries values natively. Stop rejecting irreducible CFGs — the mux handles them with linear growth.

**C3 — "One multiplexer construction for all three roles" is real and sound.** MLIR uses the SAME `EdgeMultiplexer` (`CFGToSCF.cpp:212-387`), parameterized by the edge set plus `extraArgs`, for all three roles:
- (i) **Multi-entry irreducible loop headers:** `createSingleEntryBlock` (`CFGToSCF.cpp:518-536`), called from `transformCyclesToSCFLoops` for entry+back edges when `entryEdges.size() > 1` (`CFGToSCF.cpp:821-831`).
- (ii) **Multi-exit loop latches (`shouldRepeat`):** `createSingleExitingLatch` (`CFGToSCF.cpp:552-635`) calls the same `EdgeMultiplexer::create`, passing the repeat/exit discriminator as `extraArgs` (`CFGToSCF.cpp:571-573`; comment at `:561-565`: "We pass an additional argument to the multiplexer block which indicates whether the latch was reached from what was originally a back edge or an exit block"); back edges redirected with `shouldRepeat=1`, exit edges with `shouldRepeat=0` (`CFGToSCF.cpp:588-593`); then a `createConditionalBranch` on the `shouldRepeat` arg (the last block argument) makes the single back edge (`CFGToSCF.cpp:597-605`), and `createSwitch` with the header excluded dispatches the remaining exits (`CFGToSCF.cpp:617-618`).
- (iii) **Multi-predecessor branch continuations:** `transformToStructuredCFBranches` creates a single entry into Region T via the same multiplexer when there are multiple entry blocks into the continuation (algorithm prose at `CFGToSCF.cpp:108-110`).

The only role-specific wrinkle is that the latch carries its repeat/exit bit as an `extraArgs` block argument rather than via the multiplexer's intrinsic switch discriminator, and uses a conditional branch (not a switch) for the back-edge/exit split. **Verdict C3:** Unifying all three behind one mechanism is sound and standard — it is exactly what upstream does. Implement the latch's `shouldRepeat` as an extra carried argument on the same mux; do not build a separate construct.

**C4 — CFGToSCF mutates-then-lifts; adopt that architecture.** The driver `mlir::transformCFGToSCF` (`CFGToSCF.cpp:1300+`) physically mutates the region in place: it runs `createSingleExitBlocksForReturnLike` then invalidates dominance because "the exit combiner has added new blocks and edges" (`CFGToSCF.cpp:1343-1345`); its worklist calls `transformCyclesToSCFLoops` (inserting mux/latch blocks, redirecting edges) and invalidates dominance because "blocks have been moved, created and added" (`CFGToSCF.cpp:1362-1365`); `transformToStructuredCFBranches` invalidates dominance again after "having changed its control flow edges and dominance" (`CFGToSCF.cpp:1110-1114`). Mutating functions: `EdgeMultiplexer::create`/`redirectEdge`/`createSwitch`, `createSingleEntryBlock`, `createSingleExitingLatch`, `transformToReduceLoop`, `transformCyclesToSCFLoops`. Read-only: `calculateCycleEdges`, `checkTransformationPreconditions`, dominance queries. The structured op is created only AFTER mutation (`createStructuredDoWhileLoopOp` at `CFGToSCF.cpp:872-875`), with blocks physically moved into a new `Region loopBody` (`CFGToSCF.cpp:859-866`). **Verdict C4:** For a strict no-duplication, value-yielding SCF target, **prefer mutate-then-lift**: normalize every multi-entry/multi-exit situation to single-entry/single-exit via the mux *first*, then run a trivial lift. This is more maintainable and avoids multi-entry corner cases precisely because the lift never sees a multi-entry region — the mux already collapsed it. An analyze-and-build walk must instead handle multi-entry inline at every recursion, multiplying corner cases.

**C5 — Soundness pitfalls.**
- *(a) Undef/poison fill:* The exact condition (`transformToReduceLoop`, `CFGToSCF.cpp:735-757`): when an escaping value's defining block does not dominate a latch predecessor (and the value is not itself a latch arg), a latch block-argument is added and each predecessor passes the value if the defining block dominates it (`loopBlockDominates(*iter)`), else `getUndefValue` (`CFGToSCF.cpp:751-752`). Reduce form is defined (`CFGToSCF.cpp:639-643`) as (0) no value defined in the loop body is used outside it, and (1) exit-block args = header args = back-edge operands. The correctness condition: a carried value may only flow on an edge where it is defined/dominates; on edges where it does not, undef is mandatory and *safe because that path provably never reads it*. If mis-set (passing a real but undominated value, or reading an undef on a live path), you get use-before-def / wrong-value miscompiles. A second undef sweep fills new header args on non-latch entry edges (`CFGToSCF.cpp:779-792`).
- *(b) Discriminator with no native switch:* A nested compare chain is sound and deterministic provided the discriminator values are distinct constants and the chain is exhaustive with a default (mirroring `createSwitch`'s last-case-as-default at `CFGToSCF.cpp:349-350`). The determinism risk is upstream: entry/mutual-loop-entry ordering must be deterministic — LLVM fixed exactly this non-determinism bug in `WebAssemblyFixIrreducibleControlFlow` (commit 3648370a, D74999, "we already sorted the blocks when fixing up a set of mutual loop entries, however, there can be multiple sets of such mutual loop entries, and the order we encounter them should not be random, so sort them too"). Sort your entries.
- *(c) Phi/block-argument unification across entries with differing arg sets:* The mux appends the union of all distinct successors' block arguments and records per-entry offsets in `blockArgMapping` (`CFGToSCF.cpp:239-245`); entries that don't target a given successor pass undef for those slots (`CFGToSCF.cpp:309-311`), the discriminator is set via `getSwitchValue` (`:297-300`), and extra args go at the tail (`:304-306`). This is the standard SSA-phi→block-argument unification; the pitfall is the offset bookkeeping and ensuring undef on every inactive range.
- *(d) Multiple return-like exits — why "lift" not "convert":* `CFGToSCF.cpp:22-34` states the pass first routes every return-like op to a single per-kind exit block (`ReturnLikeExitCombiner`, `CFGToSCF.cpp:419-465`, keyed by `ReturnLikeOpEquivalence` so same-kind/same-attrs ops share a block); if there are multiple *kinds* of return-like op, multiple exit blocks remain and "the transformation leaves behind a conditional control flow graph operation that dispatches to the given regions terminating with different kinds of return-like operations." Only with a single return-like kind is it guaranteed that no CFG ops remain (`CFGToSCF.cpp:31-34`). **This is the precise limitation.** Because your target permits early `return`/`throw` as region terminators, you sidestep the *residual switch* for the common case: each return-like exit becomes a region terminator (BreakOp/early-return) rather than something funneled to one block. You still cannot eliminate a genuine multi-kind dispatch where two different terminator op-kinds are reached on data-dependent paths — but with early-return terminators that residual becomes an ordinary IfOp/dispatch yielding to the enclosing region, not an un-liftable CFG remnant.

## Details
The MLIR pass is a literal implementation of Bahmann 2015 (header `CFGToSCF.cpp:9-13`), translating any single-entry/single-exit region — including irreducible CFGs (`CFGToSCF.cpp:15-20`) — into do-while loops plus conditional dispatch regions, applied recursively. The two phases are (1) cycle lifting and (2) conditional-branch lifting (`CFGToSCF.cpp:36-41`). The multiplexer (`CFGToSCF.cpp:48-90` ASCII diagrams) reroutes all edges into a region's entry blocks to a new block `bbM` that dispatches by discriminator — and the identical construct builds the latch ("A similar transformation is done to create the latch block with the single back edge and loop exit edge," `CFGToSCF.cpp:83-84`).

`EdgeMultiplexer::create` (`CFGToSCF.cpp:225-261`) inserts a new block after the first entry block, copies each distinct successor's block arguments, adds the discriminator only if there is more than one distinct successor, and appends caller-supplied `extraArgs`. `redirectEdge` (`CFGToSCF.cpp:271-316`) fills the discriminator with `getSwitchValue`, real operands for the targeted successor's slots, `extraArgs` at the tail, and `getUndefValue` for every other successor's slots, then `edge.setSuccessor(multiplexerBlock)`. This is the single point where undef-fill correctness lives. `transformCyclesToSCFLoops` (`CFGToSCF.cpp:800-893`) wires it together: `createSingleEntryBlock` over entry∪back edges (`:826`), `createSingleExitingLatch` (`:836`), `transformToReduceLoop` (`:849`), then `createStructuredDoWhileLoopOp` (`:872-875`) — mutation strictly before op creation.

Reduce form (`CFGToSCF.cpp:637-653`) deliberately mirrors LLVM's LCSSA ("the requirement of (0) is shared with LCSSA form in LLVM") but is simpler because the loop is already structured (single latch), so no general SSA updater/dominator machinery is needed — escapes are caught by walking uses up to the loop's region level (`CFGToSCF.cpp:717-727`) and promoted to header+exit block arguments (`CFGToSCF.cpp:730-733`), with a per-block dominance cache (`:709-715`).

RVSDG context: jlm (Reissmann, github.com/phate/jlm) constructs RVSDGs from LLVM IR via Control Flow Restructuring (CFR = Bahmann's loop+branch restructuring) then structural analysis; θ-nodes are tail-controlled (do-while) loops, γ-nodes are symmetric-split conditionals — the same shapes CFGToSCF emits. numba-scfg (formerly numba-rvsdg, renamed early 2025) implements Bahmann §4.1/§4.2 ("loop restructuring" and "branch restructuring") directly in Python. All three confirm the same value-region target and duplication-free predication strategy.

## Recommendations
1. **Keep CFGToSCF as your model (decision a = YES).** It is the only duplication-free, value-region-targeting algorithm in the set and a direct implementation of the paper you already follow. Map θ→LoopOp, γ→IfOp.
2. **Generalize the EdgeMultiplexer to the universal mechanism now (closes your stated gap).** Implement one construction parameterized by the edge set + extra args, and route all three roles through it: (i) multi-entry headers via single-entry-block over entry∪back edges; (ii) latches via the same mux with a `shouldRepeat` extra arg + a conditional branch for the single back edge; (iii) multi-pred continuations via single-entry-block. Stop rejecting irreducible CFGs. **Benchmark/threshold to change course (decision b):** prefer splitting over the mux only if ALL of (1) the irreducible region is tiny and side-effect-free, (2) the duplication factor is provably bounded far below the 2^(n−1) worst case, and (3) profiling shows the per-iteration discriminator switch dominates loop cost — otherwise never split. Realistically these rarely co-occur, so the practical answer is "never split; if dispatch is ever hot, add a downstream size-gated tail-duplication pass that leaves the mux as the correctness backstop."
3. **Adopt mutate-then-lift (decision c).** Normalize to single-entry/single-exit by physically inserting mux/latch/dispatch blocks and redirecting edges, invalidating dominance after each structural change, then run a trivial recursive lift that never encounters a multi-entry region. This is upstream's architecture and is strictly easier to keep correct than an analyze-and-build walk that must special-case multi-entry at every level.
4. **Handle the undef-fill invariant centrally.** Keep all undef/poison generation in one `redirectEdge`-equivalent and one reduce-form sweep; assert the dominance condition (value dominates the predecessor or else undef) so a mis-set fill fails loudly rather than miscompiling.
5. **Sort entries deterministically** before building any mux to avoid the non-determinism class of bug LLVM hit in the WASM pass (D74999).

## Caveats
- Line numbers are from MLIR trunk ("23.0.0git") via the doxygen source view; they will drift across releases — pin to a specific commit when citing in code.
- The exponential lower bound (2^(n−1)) is from Carter–Ferrante–Thomborson POPL 2003 (pp. 106–114); Janssen–Corporaal (TOPLAS 1997) report the *empirical* blowup (235% per-procedure naive, 13.6% whole-program, vs 3% with the CNS heuristic), not the asymptotic bound — both are cited for the two distinct claims.
- "Duplication-free" for StructurizeCFG is approximate: it avoids cloning basic blocks but introduces Flow blocks and predicate networks; its real disqualifier here is the predicated-linear-flow target, not duplication.
- Whether your downstream WhileOp/ForOp post-pass cleanly recovers head-controlled loops from the do-while form CFGToSCF emits is an additional step not covered by the upstream pass; the reduce form is engineered so the loop-carried/result values coincide (condition (1)), which helps that recovery.
- `transformToStructuredCFBranches` and the `mlir::transformCFGToSCF` driver line numbers (~1100, ~1300) are approximate anchors from the doxygen cross-references; the cited dominance-invalidation comments and `createStructuredDoWhileLoopOp` call site were verified verbatim, but exact line offsets in that range should be re-confirmed against your pinned commit.
